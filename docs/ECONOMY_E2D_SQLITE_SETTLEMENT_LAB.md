# E2d Economics — SQLite durable settlement acceptance laboratory

**Status: DRAFT / UNMERGED / UNDEPLOYED.** This is a **standalone local-file research harness**, **not** an authorization to expose housing purchases or money to myaso.io players. The server Rust dependency set is untouched, no route is registered, no real account or title is imported, no deployment script is modified, and no cryptocurrency conversion or wallet exists.

## Purpose

E2c [PR #367](https://github.com/tehki/myaso/pull/367) models a single-writer **in-memory** property purchase and deterministic journal replay. E2d independently tests what changes once the **commit is persisted in a real SQLite database file**. It is **not** a claim that SQLite is the final large-realm datastore. The future canonical storage implementation requires the architecture and interface review described in the E2c `docs/ECONOMY_INTEGRATION_CONTRACT.md` branch document.

Files:

- `scripts/economics_sqlite_lab.py`: stdlib-only Python research module, file-backed SQLite schema + purchase function + test-fixture admission.
- `scripts/test_economics_sqlite_lab.py`: fake actor + separate process failure/retry tests.
- A new **additive, mandatory** step in the existing protected `.github/workflows/ci.yml`: `Validate E2d SQLite settlement recovery`. All existing combat/browser/Rust steps remain unchanged.

### How the offline test works

Run using an ordinary disposable test directory:

```bash
python -m unittest discover -s scripts -p 'test_economics_sqlite_lab.py' -v
```

`bootstrap_fixture(path)` explicitly creates **fictional** test accounts (treasury ID 1, buyers 10 and 30, seller 20), demo parcel 42, map revision 7, an imaginary seller-approved listing 50, and 2,400 nonredeemable units. The seeded `approved_consent` string is explicitly **NOT a verified signature**. Never use this bootstrap function to mint or credit game actors. If an existing database file is present, bootstrap refuses to overwrite it.

`purchase(db_path, session, intent, trusted_tick)` checks the *provided* verified-session structure against buyer intent, prior unique operation receipts, listing active/expiry/price/fee/accepted-consent reference, seller ownership and title/map revisions, buyer balance version and spendable credits, owner holdings cap, integer/revision overflow and double-entry posting conservation. **A constructed `VerifiedSession` does NOT provide real authentication**. This entry point must not be wired into game client commands.

SQLite uses **WAL, synchronous=FULL, foreign keys enabled, an explicit `BEGIN IMMEDIATE` writer transaction and checked conditional updates**. Within one commit the model changes buyer, seller and treasury balances, increments title version and moves owner, consumes the seller's listing, inserts three balanced ledger postings, allocates one monotonically incremented operation sequence, stores a unique durable receipt and writes one outbox event. A failure before COMMIT rolls everything back. A failure **after** successful COMMIT may lose the caller's acknowledgment, but a retry of the same authenticated test request returns the persisted receipt rather than executing a second transfer.

### What has been proved

Local authorized Serj development machine (standard Python 3 and SQLite stdlib):

- **109/109 unittest cases passed** (previous revocation-only phase had 94 tests; the additional issue/cap phase adds 15 tests) (earlier checkpoint-witness phase was 78/78; this phase adds 16 admission mutation regression tests) (the earlier HMAC-checkpoint phase passed 60/60; the witness phase adds 18 tests) (the preceding audited-backup phase had 44/44; the latest milestone adds 16 HMAC checkpoint tests) using separate real temporary SQLite files after the fixture consent/admission extension (the initial 14-test milestone was passed separately).
- A normal committed sale survives connection close/reopen with one set of postings, one deed owner and one outbox event.
- Retrying the same operation ID returns the same canonical receipt, even when the server logical tick moves forward. Reusing an ID with another buyer/payload is rejected.
- Invalid session identity, stale balance/deed versions, expired/revoked/self sale, overdraft, and title revision overflow fail without partial debits.
- Fault injection after debit, after title and before commit rolls back.
- **Actual child-process `os._exit(91)` kills** at those pre-commit checkpoints leave no torn transaction on reopening the file.
- A kill **after** successful COMMIT retains the receipt, listing consumption, deed change and postings; restarted retry performs no new debit.
- **Two distinct Python processes** racing for the same listing produce exactly one winner, without a double purchase; the loser receives no title or debit.
- Snapshot asserts `sum(accounts.balance) == issued_units`, one three-posting zero-sum group per receipt, one outbox entry per receipt, and a consistent committed sequence.

The `hard_exit_*` failure points deliberately terminate their **own Python process**. Invoke them only in this offline test harness and never from a game server or other important process.

### E2d+ fixture admission and exact seller consent (20 October 2026)

The in-memory-authentication gap was made explicit in the SQLite laboratory. Two additional **file-backed fixture tables** enforce that the *claimed* player ID and session epoch must have a currently active admission record, and that the listing's seller consent has a matching approved record with the **same listing, seller, parcel, title version, map revision, price, commission and expiry**. The consent must not have been revoked or consumed. The consent is **consumed atomically within the same commit** as ledger postings, title transfer, listing consumption, receipt and outbox event. Retrying a committed operation with an admitted session returns the prior receipt; an epoch revoked after commit is denied further receipt access through this experimental endpoint.

Seven additional regression tests cover forged/missing consent, revoked consent with active listing, mutated sale conditions, revoked/unknown session epochs, atomic consent consumption, safe retry and post-commit process-kill recovery with the consent state. **21/21 offline tests passed locally**, including the original crash/restart and concurrent-buyer suite. Strictness does **not** mean real admission: the test fixture inserts known IDs and epochs itself, a Python caller can still fabricate a matching `VerifiedSession`, and the `approved_consent` reference is not a verifiable signature. A production trusted admission service and cryptographically or otherwise securely attested seller authorization are still mandatory.

The conformance checks are schema/transaction tests only. They do not validate production credential issuance, seller keys, server-to-DB trust, server ticks, account ownership, anti-alt land policies, identity revocation across devices, or distributed commit.

### E2d outbox projection & consumer crash recovery (20 October 2026)

E2d now also exercises *downstream recovery* of committed property-transfer notices. The new `title_projection` table is a deliberately delayed **read-side mirror**, not the authoritative deed. The new `projection_inbox` table records the committed event sequence and SHA-256 digest of each applied outbox payload. `pending_title_events` is a bounded offline query for undelivered events. `project_title_event` applies **one trusted committed receipt** by advancing the mirror and recording inbox deduplication **within one SQLite transaction**. Repeated execution of the same event returns `already_applied`, with no second state change. Malformed or modified outbox contents are rejected against the independently stored receipt in this local fixture.

The consumer implementation has injectable failures after updating the read model but before COMMIT, before COMMIT after inserting inbox, and after COMMIT with an intentionally lost acknowledgment. Child-process `os._exit(91)` checks verify that **incomplete projection and inbox state roll back together**, whereas a completed projection can safely be retried. Two independent processes racing to project the same receipt converge on one read model version and one inbox record.

**Proof limit:** This is exactly-once *application to one local SQLite read model*, NOT exactly-once network delivery or exactly-once effects in other services. It sends **no** events to external consumers. Event digest verification is not an independently authenticated, signed integrity chain and cannot prevent someone with direct database write authority from tampering with both the receipt and event. The production protocol must use a trusted internal consumer identity, a durable asynchronous transport, recipient-side idempotency, backup/recovery and out-of-order multi-parcel event ordering.

Nine additional outbox tests cover initial lag, deduplicated retry, injected rollback, hard process kills before and after consumer COMMIT, lost acknowledgment, competing processes, tampered outbox contents, and invalid sequence/poll budgets. Together with the preceding 21 E2d tests: **30/30 local Python unittest tests passed**, including process-kill tests. Exact-head GitHub Actions CI remains mandatory; earlier CI results must not be applied to this updated commit.

### E2d restore-integrity audit and independently retained checkpoint (21 October 2026)

New stdlib-only `scripts/economics_recovery_audit.py` and `scripts/test_economics_recovery_audit.py` add an **offline** source-of-truth consistency auditor and a SQLite-native backup/restore acceptance fixture. This is not the game's persistence service.

`audit_fixture_database(path)` opens an **existing** SQLite file read-only under one snapshot and fails closed on SQLite page integrity errors, foreign-key violations, incorrectly conserved credited units, invalid treasury/ownership caps, missing committed sequence numbers, mismatched sale receipts, nonzero or missing three-posting groups, missing outbox events, consumed listing/consent disagreement, deed and seller mismatches, and read-model/inbox disagreement. A tampered transaction that preserves *total* credit supply can still be invalid; detailed receipt-to-posting checks catch one class, and an external checkpoint catches otherwise-valid-looking changed credits.

`backup_fixture_database(source, dest)` uses SQLite's supported backup API to create a consistent disposable copy, refuses to overwrite any existing destination and can copy an already committed sale including its read model/inbox state. `anchor_fixture_checkpoint(db)` returns a **test-only** expected committed sequence plus deterministic SHA-256 digest of the database's **logical rows and relevant SQL schema**, excluding storage-specific page numbers; callers must independently retain the expected value outside the database. `verify_against_trusted_anchor(restored_path, trusted_anchor)` verifies both deep internal invariants and the independently supplied expected sequence/digest. Thus, an internally consistent *old* backup is rejected if an **externally preserved later checkpoint** proves a newer purchase was committed. Deleting transaction tail entries, modifying a full-sum-preserving credit split, removing important constraints, or tampering with a posted amount is detected in the covered tests.

**Local acceptance:** **44/44 offline Python unittest tests passed** on the authorized Serj host: the original E2d 30 plus 14 new backup, integrity, and anchoring tests. The workflow's existing required SQLite step was extended to discover both `test_economics_sqlite_lab.py` and `test_economics_recovery_audit.py`; all protected multiplayer and combat checks remain untouched.

**Hard trust limit:** SHA-256 provides a deterministic fingerprint, **not authenticity**. If the expected anchor is generated from the untrusted restored backup, an attacker can make a false “green” comparison; replacing both DB and external checkpoint defeats this lab. No independent authenticated checkpoint store, signature, secure offsite backup, periodic disaster-recovery job, host power-loss validation, or production account/session identity exists. This proves process/backup consistency in a single-node disposable SQLite fixture, **not high-availability or production durability**. A real implementation must select an approved store, canonical account/parcel schema, authenticated independent checkpoint and tested migration/restore procedures under central architectural review.

### E2d externally keyed HMAC checkpoint verification (21 October 2026)

New `scripts/economics_checkpoint_auth.py` and `scripts/test_economics_checkpoint_auth.py` extend the independently retained logical checkpoint with **test-only HMAC-SHA256 authentication**. The previous recovery audit's `RecoveryAnchor(sequence,logical_sha256)` proves internal consistency and detects older state **only if the supplied expected anchor is trusted**. E2d now explicitly models one way a *separately held key* could authenticate the expected checkpoint, while still leaving **real authority, key custody and independent highest-committed sequencing unimplemented**.

`issue_fixture_checkpoint(path, realm, key_id, secret)` first audits the fictional SQLite database, then emits `AuthenticatedCheckpoint` with schema version, independently provided realm label, key ID, committed sequence, logical state/schema digest and a domain-separated HMAC over those fields. `encode_checkpoint`/`decode_checkpoint` use canonical JSON encoding, strict field/type/length validation, and reject ambiguous duplicate or unknown fields. `verify_fixture_checkpoint(path, checkpoint, expected_realm, trusted_keys, minimum_committed_sequence)` validates known realm and key identity, checks HMAC using constant-time `hmac.compare_digest`, requires the sequence to meet the trusted minimum, and **only then** checks that every row/schema detail of the audited restore matches the authenticated digest. A verifier can maintain multiple test key IDs for rotation; removing an obsolete key denies envelopes issued by it.

**Tests:** 16 additional fixture tests cover sealed genesis and settled projection, backup restore, a valid but outdated HMAC checkpoint rejected against a newer **independently trusted** sequence, newer checkpoint versus older complete database, tampering with signed fields or MAC, wrong realm/key, rotation/retirement, duplicate JSON fields, wrong JSON types, tiny keys/invalid names, invalid external sequence, balanced but unauthorized account credit redistribution, and removal of schema constraints. Combined with the preceding 44 SQLite tests, **60/60 local Python tests passed**, including real child-process crashes and two-process contention. The unchanged `Validate E2d SQLite settlement recovery` CI gate discovers all `test_economics_*.py` files.

**Explicit guarantee boundaries:** HMAC is a **message authentication code**, not a digital signature or independently auditable public proof. An HMAC key must **not** be stored in the SQLite DB, hard-coded in production or provided to player clients. The test suite uses clearly fictional, static keys. A valid **old** HMAC plus an **old** internally consistent backup cannot prove rollback by itself: only an independently retained, protected `minimum_committed_sequence` prevents accepting it. An attacker with access to the key and trusted sequence store can still forge/certify malicious data. Realm labels are caller-supplied, not a proof of a verified real shard; a cloned fixture with the same realm label and identical logical state remains indistinguishable. Key provisioning, hardware-backed custody, scheduled rotation, trusted checkpoint publishing, attested offsite backups, restore drills, authorization and storage crash-consistency under actual host failure are production decisions for Core/Infrastructure.

### E2d monotonic checkpoint witness fixture (21 October 2026)

A signed checkpoint is only a statement that an authorized test key once validated a database state. **It cannot by itself identify the *latest* committed state**. New `scripts/economics_recovery_witness.py` and `scripts/test_economics_recovery_witness.py` close that particular **fixture testing gap** by explicitly recording the highest authenticated checkpoint observed in a **separate, nonoverwriting SQLite witness file**. This is a demonstrator for an independently retained committed-watermark service, **not yet an independent trust or failure domain**.

`initialize_fixture_witness(witness_path, genesis_db, signed_checkpoint, realm, trusted_keys)` provisions a previously nonexistent file **only at sequence 0** after verifying the original database and HMAC. No repair routine may silently reset an existing missing/corrupt witness from the backup being restored. `observe_fixture_checkpoint(...)` validates HMAC/realm, audits the current economic database, and under a SQLite `BEGIN IMMEDIATE` transaction updates the separately retained witness's last **committed purchase sequence**, acknowledged **outbox projection count**, and exact logical state/schema SHA-256. It permits a duplicate observation only if the digest is exactly unchanged; it refuses decreases in either watermark and refuses a different digest at the same pair of watermarks. A completed observation persists across restart or lost acknowledgment. The consumer can advance projection progress with no new purchase, which is recorded as a separate monotonic dimension.

`verify_restore_with_witness(...)` holds a witness writer lock during verification and requires **exact equality** between the authenticated checkpoint, the restored database and the witness's recorded sequence, projected-event count and logical digest. Thus a valid old *signed* checkpoint plus an old internally consistent game backup is rejected **after the witness has advanced**. Failure and child-process `os._exit(91)` points around the separate witness COMMIT test all-or-nothing advancement. Running two witness observers against the same valid checkpoint converges on one stored tip.

**Testing evidence:** 18 new tests cover genesis, missing/reset witness, normal purchase/restore, stale signed backups, no silently advancing a witness for an unobserved economic purchase, projection progress and projected-state rollback, changed state with unchanged logical clocks, tampered witness row or HMAC/realm, concurrent observers, hard exits before/after witness commit, and acknowledgment loss. The suite deliberately demonstrates the residual failure: **rolling back the witness file *and* economic database together to authentic but stale prior copies passes local verification**. Combined with the preceding 60 tests, **78/78 local Python tests passed** on the authorized Serj development host; the required `test_economics_*.py` CI step automatically includes the new test file.

**Security and architecture boundary:**

- The witness is another file on the **same machine**; an attacker or backup job with permission to replace **both** witness and economy DB defeats anti-rollback. The real witness must live in an independently protected failure/security domain with an externally retained trusted latest-commit sequence, preferably protected by an audited monotonic external service.
- The economy transaction and witness advance use **two distinct SQLite databases** and **are not one atomic commit**. A crash after purchase commit but before witness advance leaves the latest purchase **not yet externally witnessed**. Recovery policy must fail closed until reconciliation with trusted committed receipts; it must not accept an old backup just because the witness is behind.
- The checkpoint format records purchase sequence and projected-outbox count, **not every independent mutation**. Session revocation or listing changes without advancement of either clock change the digest but cannot be witnessed by this test design; a canonical append-only mutation sequence is required before real deployment.
- `AuthenticatedCheckpoint` HMAC keys remain external, caller-supplied **test secrets**. Real key management, accountable issuance, trusted time/epoch, replication, failover, game-login identity and valid seller signatures are unimplemented. No externally delivered notification, player-facing API, shard, wallet, Moon Coin or production purchase is involved.

### E2d+ authenticated admission mutation clock (21 October 2026)

A purchase sequence counts sales, and the outbox-inbox watermark counts projected property notifications, but **neither advances when a session or listing is revoked**. The earlier E2d witness intentionally failed closed on a changed logical digest with identical clocks, preventing such revocations from being witnessed and securely replayed. The new standalone `scripts/economics_admission_mutation.py` adds a **third monotonic version** for two explicit *fictional fixture* operations: `revoke_fixture_session` and `revoke_fixture_listing`. This is **not a production revocation service**, and no real authorized actor is proven by these functions.

The E2d database schema now includes `metadata.mutation_revision` and an append-only, per-operation idempotency map `admission_mutations`. The test-only revocation methods serialize with SQLite `BEGIN IMMEDIATE`, atomically revoke either an admitted session epoch or both an active seller listing and its exact associated consent, increment the monotonic mutation revision, and record the operation ID and immutable intent in the same transaction. On timeout, retrying the *same* operation ID returns the original committed revision; conflicting idempotency reuse, nonexistent or already revoked credentials, and invalid input fail closed. Child-process kill tests cover both sides of COMMIT, and two independent processes racing on the same fictional revocation still create only one journal entry.

The recovery auditor now verifies mutation revisions **1 through N without gaps**, checks that every committed revocation actually has the required revoked session/listing/consent state, includes the journal in the logical schema/data digest, and reports `AuditReport.mutation_revision`. The **separate SQLite checkpoint witness** also records mutation revision and independently rejects decreases in *any* of the three dimensions: purchase sequence, applied projection count and revocation revision. A new `read_fixture_witness_mutation_revision` keeps the previous debug `read_fixture_witness_tip` interface compatible. A signed restore must match all three dimensions and the exact logical digest. The supported policies therefore detect rollback of a **witnessed** session/listing revocation even if no property was ever bought.

**Acceptance:** **94/94 local unittest tests passed**, comprising the previous 78 E2d SQLite/HMAC/witness tests plus 16 new tests for session and seller-listing revocation, idempotency, real concurrent processes, crash-before/after-commit recovery, historical signed-backup rollback, corrupt/missing mutation records, invalid input, revocation-versus-purchase admission, and combined purchase/outbox/revocation audit. Python sources pass `py_compile`. The required protected CI step continues discovering `test_economics_*.py` and must pass at the **new exact commit** before integration.

**Critical omissions:** Only two fictional revocations bump this third counter. External SQL edits, session creation, parcel/map changes, other account-policy mutations, key changes and production seller consent approval **do not** increment it; direct changes at unchanged clocks are rejected by exact digest comparison but cannot be safely witnessed until the canonical event/mutation sequence includes them. No real authorization backs revocation calls: any actor with direct access to the fixture database and method is trusted, and that cannot cross into the game server. This schema change is for **fresh disposable lab fixtures** only; it has no production migration or backward-compatible restore guarantee. The witness and economy database still use independent SQLite commits and can be rolled back together if hosted in the same failure domain. Before launch, a single canonical *all-state mutation journal*, secure authoritative identity, independently anchored/high-availability witness and end-to-end production migration and restore policy are mandatory.

### E2d+ session issuance and ownership-cap mutation fixtures (21 October 2026)

The previous admission mutation journal covered fictional `session_revoke` and `listing_revoke` only. A *new session epoch* or *changed property-holding cap* could previously alter persistent state without the journal version advancing. The same **offline fixture** revision and independent checkpoint witness now cover two further explicit mutation types: `session_issue` and `title_cap_change`.

`issue_fixture_session(db_path, operation_id, player_id, session_epoch)` admits a new **test-only** session epoch for an existing fictional player account. It requires the epoch to exceed every previously recorded epoch, including revoked ones, and writes the epoch plus a versioned operation journal entry in a single SQLite transaction. It does **not** verify a login credential or authorize a real user. `change_fixture_title_cap(db_path, operation_id, new_cap)` versions a simulated ownership cap in the same transaction as its mutation record; it rejects unchanged/invalid limits and a cap below currently held property counts. It does **not** update production configuration or determine appropriate balance policy. Both functions support crash injection immediately before/after COMMIT and return existing results on an exact operation-id retry while rejecting conflicting intents.

The schema's `admission_mutations.mutation_kind` whitelist now includes those two actions. The recovery audit ensures each issued epoch still exists, the final recorded cap-change intent matches the persisted policy cap, all mutation revisions remain gap-free, and every committed revocation still corresponds to the revoked target. The logical digest includes the journal and metadata. The witness's **existing third monotonic watermark** therefore advances for newly issued test epochs and policy changes, alongside purchases and outbox acknowledgments. An old backup—even if correctly signed and self-consistent—cannot be accepted against a later observed and independently retained fixture witness without detection.

**Evidence:** **109/109 local Python unittest tests passed** on authorized Serj (the earlier 94 plus 15 new tests in `scripts/test_economics_mutation_extensions.py`), with byte-compilation. Tests exercise issuance, rejection of stale/reused epochs, sign/revoke recovery, cap changes and rejection below held plots, idempotency conflicts, two concurrent processes, real child-process termination before and after COMMIT, witnessing a policy-only mutation, full purchase-plus-policy replay, and corruption/rollback rejection. Exact-head protected GitHub quality remains required; earlier CI results do not validate this change.

**Limits:** This does not create durable player authentication or authorize client-driven account creation; the caller can construct fixture requests and access the standalone file. Existing genesis test accounts/epochs/listing consent are still directly seeded rather than logged as separate genesis events. Other economic state mutations—including treasury/mint policy, map revisions, item inventory, user deletion, new deed creation and consent approvals—remain unmodeled. Real account, world and economics changes require a **single approved canonical authority**, authenticated operation provenance, migration strategy, independent witness failure domain and replay of all mutable state before any live activation.

### What this does **not** prove

- **Not a production identity/authentication system:** caller can fabricate `VerifiedSession`. No Telegram/game login, server session keys, durable player IDs, ban/ownership policy, per-account quotas across shards or seller signature/consent verification.
- **Not a production game schema:** parcel 42 is not an admitted map parcel, title transfer has no world/UI/inventory integration, no true marketplace escrow or physical-item delivery; there are no live account balances.
- **Not a distributed database:** one local SQLite database serializes writers; this does not establish multi-zone/shard atomicity, shared/network filesystem durability, HA replication, recovery-point commitments, throughput, migrations or cloud failover.
- **Not physical hardware power-loss certification:** WAL + FULL sync and process kill tests do not cover drive controller lies, corrupted sectors, host power interruption, catastrophic disk failure or backup restore. An independent, authenticated highest-committed-sequence checkpoint and reconciliation remain required.
- **Not a true resource/accounting protocol:** `issued_units` metadata and consent reference are manually fixture-seeded; no audited mint/retire API, on-chain coin, FX rate, NFT or treasury deposit/withdrawal endpoint exists.
- **Not yet a launch-approved economic policy:** default values and land caps are fixture inputs and may not govern real property, taxes, real currency sinks, maintenance, storage, dead players or PvP looting.
